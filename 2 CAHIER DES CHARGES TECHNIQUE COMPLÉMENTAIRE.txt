# 3. SUPER ADMINISTRATEUR

Le rôle Super Administrateur constitue le niveau d'administration maximal.

Il peut accéder à l'ensemble des modules.

Le Super Administrateur peut :

* consulter ;
* créer ;
* modifier ;
* désactiver ;
* réactiver ;
* affecter ;
* réaffecter ;
* valider ;
* corriger les données lorsque l'action est autorisée ;
* consulter les historiques ;
* traiter les réclamations ;
* répondre aux clients ;
* superviser les livreurs ;
* consulter les livraisons en cours ;
* consulter le suivi GPS ;
* gérer les stocks ;
* gérer les produits ;
* gérer les utilisateurs ;
* consulter les journaux d'audit.

Toute action sensible doit être enregistrée dans le journal d'audit.

# 7. AFFECTATION DES LIVREURS

L'administration doit disposer d'une action :

```text
Affecter un livreur
```

La liste doit présenter les livreurs disponibles.

Pour chaque livreur :

* nom ;
* téléphone ;
* véhicule ;
* statut ;
* nombre de livraisons actives.

Après affectation :

```text
assignedDriverId = ID du livreur
```

L'affectation doit être persistée côté serveur.

---

# 8. RÉAFFECTATION

L'administration peut réaffecter une commande.

Lors d'une réaffectation :

1. vérifier l'autorisation ;
2. enregistrer l'ancien livreur ;
3. enregistrer le nouveau livreur ;
4. enregistrer la date ;
5. enregistrer l'administrateur ayant effectué l'opération ;
6. notifier le livreur concerné ;
7. mettre à jour la commande.

L'historique ne doit pas être écrasé.

---

# 9. ANNULATION

L'annulation doit être soumise aux règles de statut définies dans le cahier des charges initial.

Une annulation doit enregistrer :

* utilisateur ;
* date ;
* raison ;
* ancien statut ;
* nouveau statut.

Si une commande a déjà entraîné une consommation de stock, les règles de restitution doivent être appliquées selon l'état de la préparation.

---

# 10. ADMINISTRATION CUISINE / KDS

L'écran Cuisine doit être conçu pour une utilisation opérationnelle.

Colonnes :

```text
NOUVELLES
↓
EN PRÉPARATION
↓
PRÊTES
```

Chaque carte commande doit afficher :

* numéro ;
* heure ;
* produits ;
* quantité ;
* options ;
* suppléments ;
* remarques ;
* temps écoulé.

Actions :

```text
Prendre en préparation
Déclarer prête
```

Une commande déclarée prête doit passer vers l'état prévu :

```text
waiting_for_driver
```

selon les règles du workflow initial.

---

# 11. PROTECTION DE LA CUISINE

Un utilisateur Cuisine ne doit pas pouvoir :

* modifier le prix d'une commande ;
* modifier le paiement ;
* affecter un livreur ;
* accéder aux paramètres administratifs ;
* gérer les comptes utilisateurs ;
* modifier les permissions.

Il doit uniquement disposer des fonctions nécessaires à son travail.

## Suppression

Une suppression ne doit pas détruire l'historique lorsqu'un ingrédient a déjà été utilisé.

Dans ce cas, utiliser une désactivation plutôt qu'une suppression physique.

# 16. UNITÉS DE STOCK

Le système doit gérer des unités cohérentes :

```text
g
kg
ml
L
pièce
```

Une unité doit être définie pour chaque ingrédient.

Les conversions nécessaires doivent être centralisées.

Exemple :

```text
1 kg = 1000 g
1 L = 1000 ml
```

---

# 17. ADMINISTRATION DES RECETTES

Une recette est liée à un produit.

Structure :

```text
Produit
│
├── Ingrédient A → quantité
├── Ingrédient B → quantité
└── Ingrédient C → quantité
```

L'administration doit pouvoir :

* créer une recette ;
* ajouter un ingrédient ;
* modifier une quantité ;
* supprimer un ingrédient ;
* calculer le coût théorique.

---

# 18. COÛT THÉORIQUE

Le coût d'un produit doit être calculable à partir des ingrédients.

Formule :

```text
Coût recette =
Σ (quantité utilisée × coût unitaire)
```

Le système doit conserver les unités cohérentes avant calcul.

# 28. LIVRAISON ET ENCAISSEMENT

Ces deux événements restent indépendants.

Exemple valide :

```text
order_status = delivered
payment_status = to_collect
```

Le statut de paiement ne doit devenir :

```text
paid
```

qu'après confirmation réelle de l'encaissement.

# 30. SUIVI GPS TEMPS RÉEL

## Déclenchement

Le GPS est activé lorsque le livreur commence effectivement une livraison.

Condition :

```text
order_status = delivering
```

et :

```text
assignedDriverId = driver connecté
```

---

# 31. AUTORISATION GPS

Le livreur doit explicitement autoriser l'accès à la localisation de son appareil.

Si l'autorisation est refusée :

* la livraison doit rester identifiable ;
* le système doit indiquer que le GPS n'est pas disponible ;
* aucune fausse position ne doit être générée.

---

# 32. DONNÉES GPS

Chaque position peut contenir :

```text
latitude
longitude
accuracy
speed
heading
timestamp
driver_id
order_id
```

Le serveur vérifie :

* coordonnées valides ;
* utilisateur authentifié ;
* livreur affecté ;
* commande active ;
* fréquence acceptable.

---

# 33. GOOGLE MAPS

```text
     itinéraire

        ↓

```

# 34. CARTE ADMINISTRATION

L'administration doit pouvoir voir les livraisons actuellement actives sur une carte.

Pour chaque livraison :

* commande ;
* livreur ;
* statut ;

---

# 35. FIN DU SUIVI GPS

Le partage GPS doit être arrêté lorsque la livraison est terminée.

Condition :

```text
order_status = delivered
```

La dernière position peut être conservée selon la politique de rétention définie.

---

# 36. ABSENCE DE SIGNAL GPS

Si aucune nouvelle position n'arrive :

```text
Dernière position reçue :
il y a X minutes
```

Le système ne doit jamais afficher cette position comme si elle était actuelle.

# 53. PERMISSIONS

## CLIENT

Peut :

* voir ses données ;
* voir ses commandes ;
* créer ses commandes ;
* voir ses commandes ;
* créer une réclamation pour ses commandes autorisées ;
* envoyer des messages dans ses réclamations ;
* ajouter ses photos ;
* voir le suivi de ses commandes ;
* voir le GPS d'une livraison qui lui appartient.

Ne peut pas :

* voir les autres clients ;
* voir les autres commandes ;
* voir les données internes ;
* voir les autres réclamations ;
* voir les positions GPS d'autres commandes.

---

# 54. CUISINE

Peut :

* voir les commandes destinées à la préparation ;
* modifier les statuts de préparation autorisés ;
* consulter les informations nécessaires à la production.

Ne peut pas :

* modifier paiement ;
* gérer livreurs ;
* gérer utilisateurs ;
* consulter les réclamations administratives sauf autorisation spécifique ;
* modifier les paramètres globaux.

---

# 55. LIVREUR

Peut :

* voir ses missions ;
* consulter les informations nécessaires à ses livraisons ;
* mettre à jour les statuts autorisés ;
* envoyer sa position pendant une livraison active ;
* confirmer livraison ;
* confirmer encaissement ;
* consulter ses statistiques.

Ne peut pas :

* voir les missions d'autres livreurs ;
* modifier les prix ;
* gérer le stock ;
* gérer les utilisateurs ;
* accéder aux réclamations administratives ;
* modifier une commande qui ne lui appartient pas.

---

# 56. ADMINISTRATION

Le Super Administrateur dispose de l'ensemble des droits définis dans le système.

Les permissions doivent néanmoins être contrôlées côté backend et non uniquement masquées dans l'interface.

```text
Paiements              own       -        own      all
Utilisateurs            -         -         -       CRUD
Audit                   -         -         -       read
Paramètres              -         -         -       CRUD
```

`own` signifie uniquement les ressources appartenant à l'utilisateur.

---

# 58. PROTECTION DES RESSOURCES

Toute API manipulant une ressource doit effectuer :

```text
Authentification
↓
Vérification du rôle
↓
Vérification de propriété
↓
Vérification de l'état
↓
Action
```

Exemple :

Un livreur ne doit pas pouvoir modifier :

```text
/order/123
```

simplement parce qu'il connaît l'identifiant.

Le serveur doit vérifier que la commande lui est affectée.

---

# 59. TRACKING TOKEN

Le token de suivi doit être :

* généré côté serveur ;
* suffisamment aléatoire ;
* unique ;
* non prédictible ;
* associé à une seule commande.

Format cible :

```text
8 caractères
```

La consultation par token doit toujours respecter les données autorisées à l'exposition publique.

# 64. IDEMPOTENCE

Les opérations sensibles doivent éviter les doubles traitements.

Exemple :

Un clic répété sur :

```text
Confirmer encaissement
```

ne doit pas créer deux paiements.

Même principe pour :

* consommation stock ;
* création commande ;
* affectation ;
* livraison ;
* résolution.

# 66. SÉCURITÉ DES PHOTOS ET FICHIERS

Les utilisateurs ne doivent pas pouvoir accéder aux fichiers privés simplement en devinant leur URL.

Un client A ne doit jamais pouvoir récupérer une photo de la réclamation du client B.

# 67. SÉCURITÉ GPS

Le GPS doit être associé à :

```text
driver_id
order_id
```

Le serveur doit vérifier que le livreur est réellement affecté à la commande.

Une requête GPS provenant d'un autre utilisateur doit être rejetée.

# 68. DONNÉES GPS ET CLIENT

Il ne reçoit pas :

* historique global du livreur ;
* autres commandes ;
* autres clients ;
* informations internes.
