# BEBBA Healthy Food

## Cahier des charges technique — À compléter

**Slogan officiel : « Vos Plats santé en un clic »**

### Statut du document

Ce document constitue le **troisième cahier des charges** du projet BEBBA Healthy Food.

Il est **complémentaire** aux deux cahiers des charges précédents.

Il ne les remplace pas.

Il ne supprime aucune règle, fonctionnalité, contrainte ou exigence déjà définie.

Son objectif exclusif est de **compléter les éléments identifiés comme manquants ou insuffisamment détaillés** dans les deux documents précédents.

---

# 1. COMPLÉMENT — PARCOURS DE COMMANDE INVITÉ

## 1.1 Commande sans compte

Le système doit permettre à un visiteur de passer commande sans créer de compte.

Le parcours invité doit permettre :

1. consultation du catalogue ;
2. sélection d'un produit ;
3. sélection des options disponibles ;
4. ajout au panier ;
5. modification du panier ;
6. saisie des coordonnées nécessaires ;
7. saisie de l'adresse de livraison ;
8. validation de la commande ;
9. génération de la commande ;
10. génération du `trackingToken` ;
11. affichage du récapitulatif ;
12. suivi de la commande.

## 1.2 Données obligatoires

Une commande invitée doit obligatoirement disposer de :

* numéro de téléphone international complet ;
* adresse de livraison complète ;
* contenu de commande ;
* quantités ;
* prix calculés par le serveur ;
* frais de livraison ;
* total ;
* mode de paiement ;
* statut de commande ;
* statut d'encaissement.

## 1.3 Compte après commande

Le système peut proposer au client invité de créer un compte après la commande.

La création du compte ne doit pas modifier la commande existante.

La commande doit rester liée au client correspondant au numéro de téléphone.

## 1.4 Unicité du client

Le client ne choisit pas son identifiant technique.

L'identifiant client doit être généré à partir du numéro de téléphone international complet, sans `+`, espaces ou séparateurs.

Exemple :

`+216 98123456`

devient :

`0021698123456`

Un même numéro international ne doit correspondre qu'à un seul client.

# 2. COMPLÉMENT — GESTION DES ADRESSES

## 2.1 Adresse complète

L'adresse doit pouvoir contenir :

* pays ;
* gouvernorat ;
* ville ;
* zone ;
* adresse ;
* complément d'adresse ;
* bâtiment ;
* étage ;
* appartement ;
* indication d'accès ;
* latitude ;
* longitude ;
* libellé de l'adresse.

## 2.2 Adresse principale

Un client connecté peut disposer de plusieurs adresses.

Une seule adresse peut être définie comme adresse principale.

## 2.3 Adresse utilisée pour une commande

La commande doit conserver une copie des informations d'adresse utilisées au moment de la commande.

Une modification ultérieure du carnet d'adresses du client ne doit pas modifier l'adresse historique d'une commande.

## 2.4 Validation

Le serveur doit vérifier les champs obligatoires.

Une adresse incomplète ne doit pas permettre la validation de la commande.

## 2.5 Géolocalisation

La latitude et la longitude peuvent être associées à l'adresse.

Elles ne doivent pas être considérées comme obligatoires si le client refuse la géolocalisation et fournit une adresse exploitable.

# 3. COMPLÉMENT — CALCUL DES FRAIS DE LIVRAISON

## 3.1 Principe

Les frais de livraison ne sont pas systématiquement gratuits.

Le montant doit être déterminé par les règles commerciales configurées dans l'administration.

## 3.2 Données utilisées

Le calcul peut utiliser :

* zone ;
* distance ;
* adresse ;
* montant de commande ;
* seuil de gratuité ;
* règles commerciales actives.

## 3.3 Calcul serveur

Le montant final des frais de livraison doit être calculé et validé côté serveur.

Le navigateur ne doit jamais pouvoir imposer son propre montant.

## 3.4 Conservation

La commande doit conserver :

* montant avant livraison ;
* frais de livraison ;
* éventuelle remise ;
* total final.

## 3.5 Modification

Une modification de la configuration tarifaire ne doit pas modifier rétroactivement les commandes existantes.

# 4. COMPLÉMENT — PROMOTIONS ET AVANTAGES COMMERCIAUX

## 4.1 Administration

L'administration doit pouvoir créer, modifier, activer, désactiver et archiver des promotions.

## 4.2 Données d'une promotion

Une promotion doit pouvoir définir :

* nom ;
* description ;
* code éventuel ;
* type ;
* valeur ;
* période de validité ;
* nombre maximal d'utilisations ;
* nombre maximal par client ;
* montant minimum de commande ;
* catégories concernées ;
* produits concernés ;
* clients concernés ;
* conditions de cumul ;
* statut actif/inactif.

## 4.3 Types

Le système doit pouvoir gérer au minimum :

* remise fixe ;
* remise en pourcentage ;
* livraison gratuite ;
* avantage lié à la création d'un compte.

## 4.4 Validation

Toutes les règles doivent être contrôlées côté serveur.

## 4.5 Historique

L'application doit conserver la promotion appliquée à chaque commande.

Une modification ultérieure de la promotion ne doit pas modifier l'historique.

* ajouter une image ;

## 5.3 Association

Une image doit être associée à un produit identifié.

## 5.4 Affichage

# 6. COMPLÉMENT — DISPONIBILITÉ DES PRODUITS

## 6.1 États

Un produit doit pouvoir être :

* disponible ;
* indisponible ;
* temporairement indisponible ;
* archivé.

## 6.2 Produit indisponible

Un produit indisponible ne doit pas pouvoir être ajouté à une nouvelle commande.

## 6.3 Produit déjà présent dans un panier

Si un produit devient indisponible alors qu'il se trouve dans un panier, le serveur doit le détecter lors de la validation.

La commande ne doit pas être créée avec un produit devenu indisponible.

## 6.4 Commandes existantes

La désactivation d'un produit ne doit pas supprimer son contenu dans les commandes historiques.

---

# 7. COMPLÉMENT — PANIER

## 7.1 Persistance

Le panier doit pouvoir être conservé :

* pour un invité ;
* pour un client connecté.

## 7.2 Connexion du client

Lorsqu'un invité se connecte ou crée un compte, le système doit définir explicitement le comportement du panier.

Le système doit éviter :

* duplication des lignes ;
* perte du panier ;
* quantité incohérente.

## 7.3 Revalidation

Avant validation de commande, le serveur doit recalculer :

* produits ;
* quantités ;
* options ;
* prix unitaires ;
* sous-totaux ;
* promotions ;
* livraison ;
* total.

## 7.4 Prix modifié

Si le prix a changé depuis l'ajout au panier, le serveur doit utiliser le prix actuel valide.

Le client doit être informé du changement avant validation finale.

## 7.5 Produit supprimé

Un produit supprimé ou désactivé doit être signalé avant validation.

## 7.6 Expiration

Le comportement d'expiration du panier doit être déterministe et documenté.

Un panier expiré ne doit pas générer de commande.

---

# 8. COMPLÉMENT — CYCLE COMPLET DE L'ENCAISSEMENT COD

## 8.1 Principe

Le paiement est effectué à la livraison.

La livraison et l'encaissement sont deux événements distincts.

## 8.2 États

Le système doit distinguer au minimum :

* `to_collect`
* `paid`

## 8.3 Livraison sans paiement

Une commande peut être :

`delivered + to_collect`

Elle ne doit pas être automatiquement considérée comme payée.

## 8.4 Paiement exact

Le livreur valide le montant réellement encaissé.

## 8.5 Paiement supérieur

Le système doit enregistrer :

* montant dû ;
* montant reçu ;
* monnaie rendue.

## 8.6 Paiement insuffisant

Un montant inférieur au montant dû doit être explicitement traité.

Le système ne doit pas transformer automatiquement `to_collect` en `paid`.

## 8.7 Correction

Toute correction d'un encaissement doit :

* être autorisée ;
* conserver l'ancienne valeur ;
* conserver la nouvelle valeur ;
* enregistrer l'auteur ;
* enregistrer la date ;
* conserver le motif.

## 8.8 Encaissement par l'administration

Le Super Admin doit pouvoir confirmer l'encaissement lorsqu'il prend exceptionnellement en charge cette opération.

## 8.9 Historique

Chaque opération financière doit être historisée.

## 8.10 Idempotence

Une même confirmation d'encaissement répétée ne doit pas créer plusieurs opérations.

---

# 9. COMPLÉMENT — ANNULATION ET REMBOURSEMENT

## 9.1 Annulation

Le système doit définir les états dans lesquels une commande peut être annulée.

## 9.2 Autorisations

Les droits d'annulation doivent dépendre du rôle et de l'état de la commande.

## 9.3 Avant préparation

Une annulation avant consommation de stock doit être traitée sans créer de consommation définitive.

## 9.4 Après consommation

Si du stock a déjà été consommé, le système doit appliquer la règle de restitution définie par l'état réel de préparation.

## 9.5 Remboursement

Si un remboursement devient nécessaire, le système doit conserver :

* montant ;
* motif ;
* auteur ;
* date ;
* référence de l'opération ;
* état.

## 9.6 Paiement COD

Une commande COD non encaissée ne doit pas être traitée comme une commande nécessitant un remboursement d'un paiement inexistant.

---

# 10. COMPLÉMENT — MOMENT EXACT DE CONSOMMATION DU STOCK

## 10.1 Source

La consommation doit être calculée à partir de la recette applicable au produit.

## 10.2 Moment

Le système doit définir un point unique et déterministe de consommation du stock.

Ce point doit être identique pour toutes les commandes sauf règle métier explicitement définie.

## 10.3 Une seule consommation

Une transition répétée ne doit pas consommer deux fois le même stock.

## 10.4 Annulation

Une annulation après consommation doit appliquer la règle de restitution prévue.

## 10.5 Modification

Une modification de quantité doit recalculer uniquement la différence nécessaire.

---

# 11. COMPLÉMENT — RUPTURE DE STOCK

## 11.1 Détection

Le système doit détecter les quantités insuffisantes avant une opération qui les consomme.

## 11.2 Commande

Une commande ne doit pas consommer une quantité négative.

## 11.3 Interface cuisine

La cuisine doit recevoir une indication claire lorsqu'une préparation est bloquée par manque d'ingrédient.

## 11.4 Administration

L'administration doit pouvoir identifier :

* ingrédient manquant ;
* quantité disponible ;
* quantité nécessaire ;
* commandes concernées.

## 11.5 Blocage

Le comportement de la commande bloquée doit être déterministe et historisé.

---

# 12. COMPLÉMENT — COMPTES ADMINISTRATEURS

## 12.1 Gestion

Le Super Admin doit pouvoir :

* créer un compte administratif ;
* désactiver ;
* réactiver ;
* modifier les informations autorisées ;
* réinitialiser un accès ;
* désactiver définitivement selon la politique prévue.

## 12.2 Sécurité

Un mot de passe ne doit jamais être stocké en clair.

## 12.3 Sessions

La session doit être invalidable.

## 12.4 Révocation

Un compte désactivé ne doit plus pouvoir effectuer d'opérations protégées.

## 12.5 Historique

Les opérations administratives sensibles doivent être auditées.

# 16. COMPLÉMENT — MODE HORS-LIGNE DU LIVREUR

## 16.1 Détection

L'interface livreur doit détecter la perte de connexion.

## 16.2 Données

Les données nécessaires au travail courant doivent pouvoir être conservées localement selon une politique sécurisée.

## 16.3 Actions hors ligne

Toute action non autorisée hors ligne doit être explicitement bloquée.

## 16.4 Synchronisation

Lors du retour réseau :

1. les actions locales autorisées sont synchronisées ;
2. le serveur vérifie leur validité ;
3. les conflits sont détectés ;
4. les opérations déjà exécutées ne sont pas répétées.

## 16.5 GPS

Le GPS doit être traité séparément de la connexion réseau.

Une position obtenue hors connexion peut être mise en attente de synchronisation si cette fonctionnalité est activée.

* le livreur change significativement de trajectoire ;
* la destination change ;
* la durée devient obsolète ;
* le service cartographique demande une actualisation.

## 18.2 Données affichées

Les données affichées doivent être distinguées des données métier de la commande.
