# BEBBA Healthy Food

## Cahier des charges technique — À compléter

**Slogan officiel : « Vos Plats santé en un clic »**

---

## STATUT DU DOCUMENT

Ce document constitue le **troisième cahier des charges** du projet BEBBA Healthy Food.

Il est **complémentaire** aux deux cahiers des charges précédents.

Il ne les remplace pas.

Il ne supprime aucune règle, fonctionnalité, contrainte ou exigence déjà définie.

Son objectif exclusif est de **compléter les éléments identifiés comme manquants ou insuffisamment détaillés** dans les deux documents précédents.

# 2. PARCOURS DE COMMANDE INVITÉ

## 2.1 Commande sans compte

Le système doit permettre à un visiteur de passer une commande sans créer obligatoirement un compte.

Le parcours doit permettre :

1. consultation du catalogue ;
2. sélection d'un produit ;
3. sélection des options ;
4. ajout au panier ;
5. modification du panier ;
6. saisie des coordonnées ;
7. saisie de l'adresse ;
8. validation ;
9. création de la commande ;
10. génération du suivi ;
11. affichage du récapitulatif ;
12. suivi de la commande.

## 2.2 Données obligatoires

Une commande invitée doit disposer au minimum de :

* numéro de téléphone ;
* adresse de livraison ;
* contenu de commande ;
* quantités ;
* prix ;
* frais de livraison ;
* total ;
* mode de paiement ;
* statut de commande ;
* statut d'encaissement.

## 2.3 Création de compte après commande

Le client invité peut être invité à créer un compte après sa commande.

La création d'un compte ne doit pas modifier la commande déjà créée.

## 2.4 Identifiant client

Le client ne choisit pas son identifiant.

L'identifiant client est généré à partir du numéro de téléphone international complet.

Le numéro doit être normalisé sans :

* signe `+` ;
* espaces ;
* séparateurs.

Exemple :

`+216 98123456`

devient :

`0021698123456`.

Un numéro international complet ne peut correspondre qu'à un seul client.

## 3.1 Données d'adresse

Une adresse doit pouvoir contenir :

* pays ;
* gouvernorat ;

* zone ;
* adresse ;
* complément ;
* bâtiment ;
* étage ;
* appartement ;
* indications d'accès ;
* latitude ;
* longitude ;
* libellé.

## 3.2 Plusieurs adresses

Un client connecté peut enregistrer plusieurs adresses.

Une adresse peut être définie comme adresse principale.

## 3.3 Adresse d'une commande

La commande doit conserver les données de l'adresse utilisées lors de sa création.

Une modification ultérieure du carnet d'adresses ne doit pas modifier une ancienne commande.

## 3.4 Validation

Les champs obligatoires doivent être contrôlés côté serveur.

# 4. FRAIS DE LIVRAISON

## 4.1 Principe

Les frais de livraison ne sont pas systématiquement gratuits.

Ils doivent être déterminés par les règles commerciales configurées.

## 4.2 Données utilisées

Le calcul peut dépendre notamment de :

* zone ;
* distance ;
* adresse ;
* montant de commande ;
* seuil de gratuité ;
* règle commerciale.

## 4.3 Calcul serveur

Le montant final doit être calculé et vérifié côté serveur.

Le client ne peut pas imposer son propre montant.

## 4.4 Conservation

La commande doit conserver :

* montant produits ;
* frais de livraison ;
* remise éventuelle ;
* total final.

Une modification ultérieure du tarif de livraison ne doit pas modifier les anciennes commandes.

# 7. DISPONIBILITÉ DES PRODUITS

## 7.1 États

Un produit peut être :

* disponible ;
* indisponible ;
* temporairement indisponible ;
* archivé.

## 7.2 Produit indisponible

Un produit indisponible ne peut pas être ajouté à une nouvelle commande.

## 7.3 Produit déjà présent dans un panier

Si un produit devient indisponible alors qu'il se trouve dans un panier, le serveur doit le détecter avant la validation.

La commande ne doit pas être créée avec ce produit.

## 7.4 Historique

La désactivation d'un produit ne doit pas modifier les commandes historiques.

---

# 8. PANIER

## 8.1 Persistance

Le panier doit pouvoir être conservé pour :

* un invité ;
* un client connecté.

## 8.2 Connexion

Lorsqu'un invité se connecte ou crée un compte, le système doit gérer explicitement la fusion ou conservation des paniers.

Il ne doit pas y avoir :

* perte silencieuse ;
* duplication ;
* incohérence de quantité.

## 8.3 Revalidation

Avant validation, le serveur doit recalculer :

* produits ;
* quantités ;
* options ;
* prix ;
* sous-totaux ;
* promotions ;
* livraison ;
* total.

## 8.4 Changement de prix

Si un prix change avant la validation, le serveur utilise le prix actuellement valide.

Le client doit être informé du changement.

## 8.5 Produit supprimé ou indisponible

Le client doit être informé avant validation.

## 8.6 Expiration

Le comportement d'expiration du panier doit être déterministe.

Un panier expiré ne doit pas pouvoir créer une commande.

# 9. CYCLE COMPLET DE L'ENCAISSEMENT COD

## 9.1 Principe

Le paiement s'effectue à la livraison.

La livraison et l'encaissement sont deux événements distincts.

## 9.2 États

Le système utilise au minimum :

* `to_collect` ;
* `paid`.

## 9.3 Livraison sans paiement

Une commande peut être :

`delivered + to_collect`.

Elle ne doit pas être automatiquement considérée comme payée.

## 9.4 Paiement exact

Le montant reçu doit correspondre au montant dû.

## 9.5 Paiement supérieur

Le système doit pouvoir enregistrer :

* montant dû ;
* montant reçu ;
* monnaie rendue.

## 9.6 Paiement insuffisant

Un paiement inférieur au montant dû ne doit pas automatiquement passer à `paid`.

## 9.7 Correction

Toute correction doit conserver :

* ancienne valeur ;
* nouvelle valeur ;
* auteur ;
* date ;
* motif.

## 9.8 Encaissement par administration

Le Super Admin doit pouvoir confirmer l'encaissement lorsqu'il prend en charge cette opération.

## 9.9 Historique

Les opérations financières doivent être historisées.

## 9.10 Idempotence

Une confirmation répétée ne doit pas créer plusieurs encaissements.

# 10. ANNULATION ET REMBOURSEMENT

## 10.1 Annulation

Le système doit définir les états permettant l'annulation.

## 10.2 Permissions

Les droits d'annulation dépendent :

* du rôle ;
* de l'état de la commande.

## 10.3 Avant préparation

L'annulation avant consommation du stock doit être traitée sans créer une consommation définitive.

## 10.4 Après consommation

Si le stock a déjà été consommé, le système applique la règle de restitution définie.

## 10.5 Remboursement

Lorsqu'un remboursement est nécessaire, il doit conserver :

* montant ;
* motif ;
* auteur ;
* date ;
* référence ;
* statut.

## 10.6 COD

Une commande COD non encaissée ne doit pas être considérée comme un paiement à rembourser.

---

# 11. MOMENT DE CONSOMMATION DU STOCK

## 11.1 Source

La consommation doit être calculée à partir de la recette applicable.

## 11.2 Moment

Le moment de consommation doit être défini de façon unique et déterministe.

## 11.3 Consommation unique

Une transition répétée ne doit jamais consommer deux fois la même quantité.

## 11.4 Annulation

Une annulation après consommation applique la règle de restitution prévue.

## 11.5 Modification de quantité

Une modification doit appliquer uniquement la différence nécessaire.

---

# 12. RUPTURE DE STOCK

## 12.1 Détection

Le système doit détecter les quantités insuffisantes avant consommation.

## 12.2 Stock négatif

Une consommation ne doit jamais permettre un stock négatif lorsque la règle métier l'interdit.

## 12.3 Cuisine

La cuisine doit recevoir une indication claire lorsqu'une préparation est bloquée.

## 12.4 Administration

L'administration doit pouvoir identifier :

* ingrédient ;
* quantité disponible ;
* quantité nécessaire ;
* commandes concernées.

## 12.5 Blocage

Le comportement de la commande bloquée doit être déterministe et historisé.
